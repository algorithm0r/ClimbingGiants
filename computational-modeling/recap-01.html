Assignment 1 5:54

Every assignment this quarter is framed as work at an engineering firm that has just hired you. In the first one your supervisors, Alice and Bob, hand you a zip file of data and leave on vacation. When they get back they want to know what you found in it. The assignment sheet does not tell you what is in the file, and that is on purpose. Real problems usually start out ill defined, and a skill most engineers need (in software or anywhere else) is turning an ill-defined request from a customer or a boss into a well-defined problem you can solve. That is the main skill the course asks you to practice. You will not be starting from scratch, though, since every assignment comes with example reports.

You will plot data almost every week, and this week the plot is the whole assignment. Get into the habit of saying what errors you found and how uncertain you are about what you present.

Errors and Assumptions 8:22

The crash data comes from a federal database of real tests, and it has errors in it. Your pack probably has one too. The first week's video describes the error Chris found in his data, but do not assume yours matches. Each test was run by a different lab and team, so one team may have made a consistent error that the others did not. Look for it in your data, and if you do not find it, go with what your data shows. Your sample rate may also differ from the 12.5 kHz on the notes page (10 kHz or 20 kHz, for instance), so check it before you write your report.

When something looks wrong, you make an assumption, and you say so in your report. A correction made silently leaves the next person who opens the data unable to follow your reasoning. Every report this quarter should show the evidence in your plot, say whether you think it is right, and list the assumptions you made along the way.

Lecture correction

The unit example came out garbled in class. One channel in Chris's data is labeled in meters, and read as meters its values come to about 32 km, which no chest moved in a crash test. The assumption that makes sense of it is that the values are micrometers, which turns 32 km into 32 mm. Check whether the same mislabel occurs in your data, and if you correct it, state the assumption in your report.

The Example Reports 11:01

Every assignment has three example reports, one for each reason you might write a report in a professional setting.

  • Memo. The shortest, and the one Chris says he would probably pick. It reads like an email back to Alice and Bob with a PDF attached. It says what was in the file (some basketball data and some crash tests), that the crash tests look like what they want, and what it found there.
  • Technical report. More formal, the kind of thing you would send a client. It has the same plots with more detail, headings, a table, and a clear statement of the error it found. Compare it with the memo to see what the shorter one leaves out.
  • Notebook. Written in Google Colab, where code and text live in one document and the code runs in place. This style is popular in machine learning. When you are done you generate a PDF with everything in it.

Chris recommends the memo (written in a Google Doc with the plots pasted in) or the notebook if Colab interests you. The technical report is mostly extra work for this assignment.

Channels 11:55

A channel is a list of measurements. When the x axis is time (which covers about 95% of what gets measured) it is also called a time series, and "channel" is the general term. A real crash test records something like 192 channels. Chris cut the files down to about eight, and your file may have a few more or fewer. The memo plots each channel with its label (head acceleration in x, y and z, for instance) and its units, which is what makes a graph readable by someone else.

Using the Code 13:53

Each example links to the program that made its plots, and you are welcome to copy it. Most of the work in this course is the physical modeling (i.e. thinking about the physical problem and how to approach it mathematically), and the programming is there to support it. You may copy and adapt the code (this is normal practice in software engineering), though make sure you read what you copied.

Your Data 17:34

The your data page builds your pack from four words. Roll your own four words (do not use the ones in Chris's demo), and everyone gets a different pack. If two people do end up with the same crash test it does not matter much. The purpose of the four words is to give each of you different data, as a team would have. Chris's pack held one crash test, 60 basketball training arcs, and 40 test arcs.

Please remember your four words. They are in the file name of the zip and in the README inside it, and you should put them on your report, so the instructors can rebuild your data and check it if something goes wrong. Inside the pack, the crash folder holds one file named for its test number (a number followed by .json). That is the file you want this week. The shots folder is for the extra problem, and you can ignore it otherwise.

Reading the File 20:04

The crash file is JSON (pronounced like the name Jason), which stands for JavaScript Object Notation. You do not need to know much about it. It is a data format that came from JavaScript, the language of web pages, and it gathers a bundle of data into one file. Here the bundle is one crash test.

VS Code 21:53

Chris opened the file in Visual Studio Code, an integrated development environment (the main software programmers write code in). Like Photoshop or AutoCAD, it opens with far more features than you need. You will likely only need one or two of them, and you can ignore the rest. The most useful one is the file explorer on the left. Make a folder for the course, with a folder for your data inside it, and you can move between files without leaving the editor (you can also drag files into it). Chris's layout was a course folder, a test folder for the day, a crash folder with two data files, and assignment1.py.

The JSON file opens as one line thousands of characters long, and even with word wrap on (in the View menu) it is hard to read. That is expected, since the file is written to be read by programs.

The Header 28:09

Each channel carries a code like 11HEADCG0000ACXP, which identifies it for the computer. You can pick out some of it ("HEAD" is the head, "AC" is acceleration), and the same information is stored in readable fields in the header. One of those is the direction. On a car the axes have names, which avoids arguing about which way x points. Longitudinal is along the direction of travel, then lateral and vertical.

The Anatomy of a measured signal page shows the header laid out readably, with the important fields highlighted (the dimension, the direction, the location, the units, and the two time fields). You can ask the chatbot to do the same for your file, either by describing what is in it or by writing a small page that displays it.

Continuous and Discrete 31:21

The gap between continuous and discrete is close to the central lesson of the course, and it will come back dozens of times. Calculus and physics assume the world is continuous, but an instrument only records discrete samples, one every so many microseconds, and each sample is a little off because of error and noise. Connect the samples and you get a jagged line, and this week you only need to plot that line. Much of the rest of the quarter is about rebuilding the continuous picture from discrete, noisy samples.

The header gives the time between samples. In the notes page's test it is 8 × 10−5 seconds, or 80 microseconds. Inverting it gives the sample rate, 1 / 0.00008 s = 12,500 Hz.

For a sense of scale 35:13, film runs at 24 frames a second and video at 30 or 60 (with some films shot at 48). That is fast enough for your eyes to see motion. Cameras that shoot thousands of frames a second exist, and they make the slow-motion hummingbird videos. The accelerometer is doing the same thing at 12,500 samples a second. Generally you want as many samples as you can get, because the curve you rebuild is closer to what happened. The next few weeks cover why a rate is chosen, and why you might sometimes lower it.

Time Zero 36:41

The header also gives the time of the first sample, and it is negative (−0.05 seconds, or 1/20 of a second). In a crash test the car is towed toward the barrier at a fixed speed, so at first the accelerometer reads zero. Then the car hits the barrier and the reading goes negative, i.e. it decelerates. Zero is set at the start of the event, the impact. Each lab records a different amount of time before impact, and the zero lets you line up the event across every record you have.

Finding a Channel by Its Code 39:07

To pull out the longitudinal head acceleration you could check the location, the direction and the dimension one field at a time. Matching the code does all of that in one check. A good first request to the chatbot is a program that lists every code in your file with what it means, so you have them on hand.

The Workbench 40:45

The workbench puts every tool on the site in one place. If the site remembers your four words (the header link then reads "Your data" followed by them, though a narrow window can cut it short), the "your data" button loads your pack. You can then switch between channels (head x, head y, chest x, vehicle x, and so on), which lets you check that a plot you made yourself looks right. Later in the quarter you can integrate your data there as well.

Student question

Q: You said there are times when fewer samples are better. For a crash test, would you not want as many timestamps as possible? 42:34

A: Yes. With nothing else constraining you, take as many points as you can. Labs that sample differently can reach different conclusions, so the field agrees on a standard that keeps their data comparable, even when that means giving up some resolution. That is, the standard is there to keep labs consistent with each other. There are one or two cases later in the quarter where a lower rate is better, and Chris will point them out.

Technically

The standard for crash data (SAE J211) does its work through filtering, which the class had not covered yet. It assigns each measurement a filter class, chosen by how quickly the measured quantity can change, and labs filter to that class so that their numbers can be compared. Week 2 covers sampling and why a rate might be lowered (Discrete evaluation), and Week 4 covers filter classes (The filter class is part of the measurement).

Running the Example Code 44:03

Almost every notes page has code, in three languages.

  • Python. The one Chris recommends, and the best fit for mechanical engineers.
  • MATLAB. The traditional choice in engineering, still widely used, and free for you as a student. Use it if you already know it.
  • JavaScript. Included because it is the code the page itself runs.

The Python and MATLAB plots on the page were made by running that code, so you see what to expect. Read the code before you paste it, and use the line-by-line highlights where a page has them.

Chris made two changes to the code on the anatomy page before running it.

  • Your test number. The page loads test 10642, which is held back from the student packs. Change it to the number of your own file.
  • plt.show(). Without it the script runs and no plot appears. The page's Python tab now includes it.

Press the play button at the top right of VS Code to run the file, and wait for it to finish before pressing it again. A window opens with the plot, and its save button writes a PNG (or a PDF) that you can paste into your report. To plot all eight channels, you can paste in each code and save each plot, or ask the chatbot to change the program so it plots every channel and saves the files for you. Use the chatbot to learn some Python along the way, but do not get bogged down in the code.

Tip: save the plot from Python

Python can also save the plot to a file for you, so you do not need the save button. Add plt.savefig before plt.show(), and the file lands in the folder you ran the program from. The extension in the file name sets the format.

plt.savefig('head_x.png', dpi=200)   # a picture to paste into a document
plt.savefig('head_x.pdf')            # a PDF, which stays sharp at any size
plt.show()

Save before you show. Once you close the plot window the figure is gone, and a savefig after plt.show() writes a blank file. To name the file after the channel instead, use plt.savefig(f"{ch['code']}.png", dpi=200), which writes 11HEADCG0000ACXP.png (handy once you plot all eight channels in a loop).
