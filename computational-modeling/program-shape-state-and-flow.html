Program shape I, state and flow

Video: Understanding Program State and Flow (for Engineers) (0:21:14). Slides

Claim

A program is described by two things: the set of named values that exist at a given moment, called its state, and the order in which those values change, called its flow. Reading a program means tracking state through flow.

What does it know right now, and what happens next. Those two questions answer most of what any program is doing.

The split will be familiar from mechanics. A free‑body diagram is a snapshot: the forces and positions that hold at one instant, with no account of how they got there. The equations of motion are the other half, and they say how that snapshot becomes the next one. State is the free‑body diagram of a program, and flow is its dynamics.

State

At any point during execution, some named values exist and have particular contents, and that collection is the state. A single number and an array of a million numbers are both state, and they are the same kind of thing, which is a name attached to contents. The array holds many measurements under one name, so a is a whole record and a[0] is its first sample. The size of the thing under the name makes no difference to how you read it.

Three questions locate any value in a program:

  • When does it start existing? The line that first assigns it.
  • What changes it? Every later line that assigns to it. If there are none, it is fixed once and can be read as a constant.
  • Is it still needed afterwards? A value that nothing reads once the loop has finished is scratch. A value the loop builds up and something reads afterwards is the result.

Flow

Flow is the order of execution. Two shapes cover almost everything in this course, and the second of them is the only one that usually needs care.

Straight line. Statements run once, top to bottom, so the state after the block follows from the state before it.

Loop. A block runs repeatedly. Some of the state is rebuilt on every pass and some carries over, and telling those apart is the first thing to do when reading one.

A value that carries between passes is an accumulator. It starts before the loop, is updated inside it, and is read after it. A value assigned fresh at the top of each pass is scratch, and its contents from the previous pass are gone. Mistaking one for the other is a common reading error, so it is worth settling which is which before reading anything else.

A Calculation You Can Check by Hand

A ball leaves your hand 2.00 m above the ground, moving upward at 5.00 m/s. When does it reach the ground? Its height is

$$y(t) = y_0 + v_0 t - \tfrac12 g t^2$$

and the ground is $y = 0$, so this is the quadratic you have been solving since school. With $g = 9.81$ m/s² it rearranges to $4.905\,t^2 - 5t - 2 = 0$, and the quadratic formula gives

$$t = \frac{v_0 + \sqrt{v_0^2 + 2 g y_0}}{g}$$

Work it through and name every value as you go. Each row below is one name and its contents, which is to say each row is a piece of state:

The other root is $-0.3073$ s, which is the same parabola crossing the ground before the ball was released. The algebra offers it and the problem does not want it. We will meet that again in week 7, when a root finder hands back a root that is real and correct and is not the one that was asked for. Here is the same computation as a program. It is straight‑line flow: six statements, each run once, top to bottom.

v0 = 5.00
g  = 9.81

root = sqrt(disc)
t    = (v0 + root) / g
y0 = 2.00;

const g  = 9.81;

const disc = v0*v0 + 2*g*y0;
const root = Math.sqrt(disc);

Reading it is the two questions from the claim: what exists at this line, and what runs next. disc does not exist until line 5, so nothing above line 5 can use it, and nothing is ever reassigned, so no name means two different things at two different moments. A straight‑line block is the easy case for exactly that reason, and it is the reason it is worth writing this way when you can.

Reading a Loop

You can check every line of that calculation on paper, and the next one you cannot. The velocity the vehicle loses during the impact is the sum of its acceleration samples multiplied by the interval between them, and the crossmember channel holds 4501 of them. The arithmetic is the same addition repeated and only the count has changed, which is what a loop is for. This is also the integral from week 3, written out longhand.

a  = load_channel(10642, '093')
dt = 8.0e-5

total = 0.0

for i in range(len(a)):
    total = total + a[i]

dv = total * dt
a  = loadChannel(10642, '093');
dt = 8.0e-5;

total = 0.0;

for i = 1:numel(a)
    total = total + a(i);
end

dv = total * dt;
const a  = await loadChannel(10642, '093');
const dt = 8.0e-5;

let total = 0.0;

for (let i = 0; i < a.length; i++) {
  total = total + a[i];
}

const dv = total * dt;

Five names exist here and they play four different roles. a and dt are input, set once and read many times. total is the accumulator, the one value that carries between passes. i is scratch, meaningless outside the loop. dv is the result, and it does not exist until the loop is finished.

Why write the loop when a.sum() exists

You should use it. The loop above is slower and longer than the library call that does the same thing, and it is easier to get wrong. Most later weeks use the library call. The loop is here because the accumulator shape turns up whether or not a library call is available, including inside the library calls themselves, and in places where you do write it out, such as the iteration count in week 7. What transfers is the shape. This particular loop does not come up again.

Reading Code

The practical consequence is a reading strategy. Read unfamiliar numerical code by finding the state and following it:

  1. Find what comes in, the arguments and the values loaded from files.
  2. Find what goes out. What is returned or plotted at the end.
  3. Find the loops, and for each one identify the accumulator. That is what the loop is for.
  4. Most of what is left is scratch, and can be skipped until you have a reason to care.

Applied to a page of unfamiliar code this is quick, and it answers what the code produces. How each line achieves it can wait.

Check
  1. In the loop above, what is the value of total before the first pass, and why does it have to be set before the loop, when setting it inside looks equivalent?
    Answer

    Zero. total = 0.0 runs once, before the loop begins, so that on the first pass there is something for total + a[i] to add to. It has to be outside because the loop body runs once per pass. Move the initialisation inside and it re-runs every pass, resetting the sum immediately before extending it. total then ends holding the last sample, and the sum of all of them is lost. An accumulator is a name whose value has to survive from one pass to the next, so it has to be created before the loop.

  2. A loop contains the line peak = a[i]. Is peak an accumulator or scratch? What single change would make it the other one?
    Answer

    As written it is scratch. peak = a[i] overwrites unconditionally, so nothing survives from one pass to the next, and after the loop peak holds the last sample while the largest is never kept. The single change is a guard:

    if a[i] > peak: peak = a[i] Now the assignment depends on what previous passes left behind, so the value carries across and peak is an accumulator. Being an accumulator, it now needs initialising before the loop, so the one change forces the other.

  3. You are handed 60 lines of unfamiliar code containing two loops. Which four things do you look for first?
    Answer
    1. Which names survive a pass and which do not. That splits the state into accumulators and scratch, and the accumulators are what the loop was written to build.
    2. Where each of those names is initialised, and whether it is inside or outside the loop. This is where the common bug lives.
    3. The bounds. Where each loop starts and stops, and whether the last index is included. Off-by-one at an array end is the other common bug.
    4. What is read after the loop finishes. That tells you what the loop was for, and anything not read afterwards was scratch whatever it looked like.

    For two loops there is a fifth question. Does the second one reset state that the first one built, and are the two nested or sequential?
