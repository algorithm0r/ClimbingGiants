Shortest Path Problem

Informal scenario: Find the lowest-cost route between two cities in a weighted road map.

Formal statement:

  • Input: Directed or undirected weighted graph $G = (V, E, w)$ with positive edge weights; source vertex $s$; destination vertex $d$.
  • Output: A path from $s$ to $d$ of minimum total weight, and that weight value.

Variants:

Variant Algorithm
Single source, single destination Dijkstra's
Single source, all destinations Dijkstra's (solves this simultaneously)
All pairs, all destinations Floyd-Warshall (2D DP)

Constraint: positive edge weights. If negative-weight cycles exist, the shortest path is undefined — one could traverse the cycle indefinitely to reduce cost. Dijkstra's algorithm requires positive weights. Bellman-Ford handles negative weights (but not negative cycles).

Why brute force fails: Exponentially many paths may exist in a graph.

Why Naive Recursion Fails

Write a self-reduction for shortest path. Let $\text{SP}(v)$ = length of the shortest path from $s$ to $v$:

$$\text{SP}(d) = \min_{v \in \text{adj}^-(d)} \{ \text{SP}(v) + w(v, d) \} $$

with base case $\text{SP}(s) = 0$.

This is exactly like the DP self-reductions from Weeks 6–7. But there is a key difference: a general graph can have cycles. Naively applying memoized recursion may circle back to previously-visited vertices without making progress, leading to infinite loops.

In the DP problems of Weeks 6–7, the subproblems were on strictly shorter lists or smaller prefixes — a natural ordering that prevents cycles. General graphs have no such ordering. We need a different approach to determine which subproblems to solve first.

Dijkstra's Algorithm

Dijkstra's algorithm is a greedy-DP hybrid: it applies the greedy idea from Week 8 (always process the most promising candidate) to compute shortest distances bottom-up, similar to DP.

Core greedy insight: Among all vertices not yet finalized, the one with the current minimum distance estimate is guaranteed to have a correct shortest-path distance. No shorter path can be found through any remaining vertex, because all edge weights are positive.

Two sets:

  • $C$ (correct/finalized): vertices whose shortest-path distance is known exactly.
  • $T$ (tentative): vertices with a current distance estimate that may still be updated.

Relax operation: For edge $(u, v)$, if $\text{dist}[u] + w(u, v) < \text{dist}[v]$, update $\text{dist}[v] = \text{dist}[u] + w(u, v)$.

Dijkstra(G, s):
  dist[s] = 0; dist[v] = ∞ for all v ≠ s.
  All vertices in T; C = {}.
  While T is not empty:
    Extract u from T with minimum dist[u]; move u to C.
    For each neighbor v of u: Relax(u, v).
  Return dist[d].  // or all dist values

Structural comparison with Prim's algorithm:

Prim's Dijkstra's
Priority queue key Edge weight $w(u, v)$ Cumulative distance $\text{dist}[u] + w(u, v)$
Goal Minimum spanning tree Shortest paths from $s$
Correctness argument Cut Property Greedy key insight

The algorithms are structurally identical; only the key stored in the priority queue differs.

Proof of Correctness

Claim: When vertex $u$ is moved from $T$ to $C$, $\text{dist}[u]$ equals the true shortest-path distance from $s$ to $u$.

Proof by contradiction: Suppose when $u$ is extracted, $\text{dist}[u] > \text{SP}(u)$. There exists a shorter path $P$ from $s$ to $u$.

Since all vertices in $C$ have correct distances (by induction) and $u \notin C$, the path $P$ must contain some vertex $x$ not yet in $C$. Let $x$ be the first vertex on $P$ not in $C$.

The subpath from $s$ to $x$ has total weight $\geq \text{dist}[x]$ (since $\text{dist}[x]$ is already the minimum known estimate, updated when the previous vertex on $P$ was extracted). The subpath from $x$ to $u$ has positive total weight (positive edge weights).

Therefore $\text{dist}[x] \leq \text{length}(P) < \text{dist}[u]$, meaning $x$ should have been extracted from $T$ before $u$. Contradiction.

Runtime Analysis

The runtime depends on the data structure used for the tentative set $T$:

Data structure Extract-min Update Total runtime
Simple array $O(|V|)$ $O(1)$ $O(|V|^2)$
Binary heap $O(\log |V|)$ $O(\log |V|)$ $O(|E| \log |V|)$
Fibonacci heap $O(\log |V|)$ $O(1)$ amortized $O(|E| + |V| \log |V|)$

The binary heap version is identical to Prim's runtime. The Fibonacci heap version is theoretically optimal but rarely used in practice due to implementation complexity.

Introduction to Complexity Theory

The previous weeks focused on algorithm analysis: given an algorithm, determine its runtime. Complexity theory asks a different question: given a problem, what is the minimum runtime any algorithm for it must use?

This is a harder question — it requires proving that no algorithm can do better, not just that a specific algorithm achieves some bound.

Goal: Classify problems by their inherent difficulty, independent of the specific algorithms we know. Identify which problems can and cannot be solved efficiently.

Decision Problems and Input Size

Decision problem: A problem whose output is always yes or no.

Every optimization problem can be converted to a decision problem by adding a threshold: "Is there a solution with cost $\leq k$?"

Decision problems are the standard unit of analysis in complexity theory because their binary output makes formal reasoning cleaner.

Input encoding: All inputs can be represented as binary strings. The input size $n$ is the number of bits in the binary encoding.

This matters enormously for integers. An integer $N$ has about $\log_2 N$ bits, so $n = \log_2 N$ and $N = 2^n$. An algorithm that runs in $O(N)$ time runs in $O(2^n)$ time in terms of input size — exponential, not polynomial.

The Complexity Class P

Polynomial time: An algorithm runs in polynomial time if its runtime is $O(n^c)$ for some constant $c \geq 0$.

Class P: The set of all decision problems solvable by a deterministic algorithm in polynomial time.

Polynomial time is the formal definition of "efficiently solvable" in complexity theory.

Why polynomial time as the threshold?

  • Polynomial algorithms compose: polynomial of polynomial is polynomial.
  • The threshold is robust to reasonable changes in encoding.
  • In practice, polynomial-time algorithms tend to be feasible while exponential-time algorithms are not.

Examples in P:

Problem Algorithm Runtime
SEARCH (sorted array) Binary search $O(\log n)$
MULT (multiply two integers) Grade-school $O(n^2)$
MST decision (is weight $\leq k$?) Prim's/Kruskal's Polynomial
Shortest path decision (is distance $\leq k$?) Dijkstra's Polynomial

Primality as a Case Study

PRIMES: Given integer $N$, is $N$ prime?

Naive trial division: Test all divisors from 2 to $\sqrt{N}$. Runtime: $O(\sqrt{N})$.

In terms of input size $n = \log_2 N$: $\sqrt{N} = 2^{n/2}$, which is exponential in $n$. Trial division is not a polynomial-time algorithm.

PRIMES was not known to be in P for a long time, despite being conceptually simple.

AKS primality test (2002): Manindra Agrawal, Neeraj Kayal, and Nitin Saxena proved PRIMES $\in$ P. Their algorithm runs in polynomial time in the number of bits.

This was a landmark result: it resolved a decades-old open question and demonstrated that even intuitive "easy" problems can take decades to classify correctly.

Other complexity classes (briefly):

  • BPP (Bounded-error Probabilistic Polynomial time): problems solvable by randomized algorithms in polynomial time with error probability $\leq 1/3$. Before AKS, probabilistic primality tests placed PRIMES in BPP.
  • BQP (Bounded-error Quantum Polynomial time): problems solvable by quantum computers in polynomial time. Shor's algorithm for integer factoring is in BQP; it is believed (but not proven) that BQP $\not\subseteq$ P.

The Complexity Class NP

Many important problems — Subset Sum, Traveling Salesman, Satisfiability — have no known polynomial-time algorithm. Brute force is exponential.

A key observation: it is often much easier to verify a proposed solution than to find one from scratch.

The Merlin/wizard thought experiment: Merlin is an all-knowing prover who claims to know the answer to a hard problem and offers a proof. Arthur (the verifier) must check Merlin's proof in polynomial time.

Example: Merlin claims that a large number $N$ is composite and offers factors $p$ and $q$. Arthur checks $p \times q = N$ and $p, q > 1$ — this check is $O(n^2)$ even if factoring $N$ from scratch might take exponential time.

This separates the difficulty of finding a solution from the difficulty of verifying one.

Class NP: The set of all decision problems that have a polynomial-time verification procedure.

NP stands for "nondeterministic polynomial time" — the historical definition uses nondeterministic Turing machines, but the verifier definition is equivalent and more intuitive.

P $\subseteq$ NP: Every problem in P is also in NP.

Proof: If a problem is in P, use the polynomial-time algorithm itself as the verifier — ignore the certificate and run the algorithm directly. The algorithm outputs yes or no in polynomial time, satisfying both correctness conditions.

Verification Procedures

A verification procedure (or verifier) takes two inputs:

  • $x$: the original problem input.
  • $w$: a certificate (also called witness or proof) — extra information provided by the prover.

It outputs yes or no.

Correctness of a verifier: Two conditions, proven separately:

  1. Completeness (yes → yes): If the answer to the original problem is yes, there exists some certificate $w$ that causes the verifier to output yes.
  2. Soundness (no → no): If the answer to the original problem is no, then no certificate $w$ causes the verifier to output yes.

The certificate must be polynomial in length. The verifier must run in polynomial time in the length of $x$.

COMPOSITES Verifier — Worked Example

COMPOSITES: Given $N$, is $N$ composite (not prime)?

Certificate: Two factors $p$ and $q$ with $p \times q = N$ and $p, q > 1$.

Verify(N, p, q):
  If p ≤ 1 or q ≤ 1: say no.
  If p × q ≠ N: say no.
  Say yes.

Proof of correctness:

  • Yes → yes: Assume $N$ is composite. Then there exist $p, q > 1$ with $p \times q = N$. Those $p, q$ pass all tests; verifier says yes. ✓
  • No → no: Assume $N$ is not composite (prime or 1). Then no factorization $p \times q = N$ with $p, q > 1$ exists. Any pair the prover offers either fails the $> 1$ check or the multiplication check. Verifier always says no. ✓

Runtime: $O(n^2)$ for the multiplication — polynomial. ✓

Verifier Design Process

  1. State the original problem input.
  2. Identify what the prover would need to tell you to make checking easy.
  3. Write type-checking tests (is the certificate a subset of the right set? is it a permutation? etc.).
  4. Write value-checking tests (does the sum equal the target? are all constraints satisfied?).
  5. Say yes if all tests pass.
  6. Prove correctness: yes → yes, and no → no (or equivalently, yes → yes backwards as the contrapositive of no → no).
  7. Verify each step runs in polynomial time.

The P vs. NP Question

P vs. NP: Is NP $\subseteq$ P? That is, does every problem whose solutions can be verified in polynomial time also have a polynomial-time algorithm that finds solutions?

This is the most famous open problem in theoretical computer science and one of the Millennium Prize Problems (with a $1 million prize for resolution).

Widely conjectured: P $\neq$ NP. Most computer scientists believe finding a solution is fundamentally harder than verifying one.

If P = NP: Every efficiently verifiable problem would also be efficiently solvable. Cryptography (which relies on the hardness of certain problems) would collapse. Many optimization problems currently requiring exponential search would have polynomial-time solutions.

Current state: Neither P = NP nor P $\neq$ NP has been proven.

Connections

Dijkstra's algorithm is structurally identical to Prim's MST algorithm from Week 8. Both grow a set of finalized vertices by always processing the minimum-priority candidate from a priority queue. The difference is only in the priority key.

The distinction between polynomial time in the numeric value of an input (e.g., $O(N)$) and polynomial time in the bit-length of the input (e.g., $O(n) = O(\log N)$) was first relevant in Week 7 for Subset Sum and Knapsack (pseudo-polynomial runtimes). The same distinction now defines the class P.

The verifier framework introduced this week is the foundation for NP-completeness in Week 10. Subset Sum, Knapsack, Clique, and Hamiltonian Cycle are all shown to be in NP via explicit verifiers — then shown to be among the hardest problems in NP via reductions.

The AKS result (PRIMES $\in$ P, 2002) illustrates that membership in P can be subtle: a problem that seems "obviously easy" can take decades of work to formally classify.
